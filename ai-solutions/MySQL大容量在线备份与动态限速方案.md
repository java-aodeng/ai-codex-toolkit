# MySQL 大容量在线备份与动态限速方案

> 用途：将持续读写的 MySQL 全实例，在线压缩备份到本地大容量硬盘，并在任务运行中调整读取速度。本文只描述可复用方案，不包含真实服务器地址、端口、账号、密钥、主机指纹或业务数据。所有尖括号占位符必须在实施环境中替换，不能原样执行。

## 1. 方案选择与适用范围

采用 **XtraBackup 物理热备 + ZSTD 压缩 + SSH 流式传输 + 本地二进制接收 + cgroup v2 动态磁盘限速**。

适合以下条件：

- MySQL 数据量较大，业务不能为了备份长时间停机。
- 数据库部署于 Linux，业务表以 InnoDB 为主。
- 服务器没有空间额外存放一份完整备份。
- 本地硬盘能够容纳压缩备份，电脑和网络可以持续在线。
- 可以在 Linux 环境恢复，并愿意做实际恢复验证。

本方案以 MySQL 8.4 系列和匹配的 XtraBackup 8.4 系列为基线；实施时核对准确版本、引擎支持和版本限制，不能随意混用其他系列的工具。

**备份范围是全实例，不排除任何持久化业务表。** 数据文件、索引、恢复所需日志及工具元数据被包含；数据库实例之外的应用文件、对象存储、Elasticsearch 索引不属于本次范围。运行时统计类虚拟表不等同于持久业务表。

核心边界：

| 能力 | 本方案说明 |
|---|---|
| 不停库备份 | 支持；仍会增加磁盘、CPU、网络负载，不承诺业务零影响 |
| 服务器不保留完整副本 | 支持；但配置、日志、临时文件仍占空间 |
| 运行中加速、降速 | 支持，调整独立备份容器的磁盘读取上限 |
| 完全停止后继续原任务 | 不支持可靠断点续传，需要重新做完整备份 |
| 传输校验 | 源端与接收端 SHA-256 比对，再重新读取落盘文件校验 |
| SQL 导入 | 不适用；输出不是 INSERT SQL 文件 |
| 恢复 | 在独立 Linux 环境解包、解压、prepare 后启动 MySQL |

## 2. 数据路径与组件职责

```text
线上 MySQL（持续处理业务）
    │ 只读访问数据文件 + 数据库备份权限
    ▼
独立 XtraBackup 容器
    │ 捕获 redo、复制数据、ZSTD 压缩
    │ 单独限制 CPU / 内存 / 数据盘读取速率
    ▼
SSH 加密传输
    ▼
本地接收程序（按块写盘、计算摘要、记录进度）
    ▼
临时文件 → 传输成功 → 正式 xbstream 文件 → 本地文件复核
```

服务器向外发送备份，因此在服务器监控中主要看 **上传/TX**；本地电脑接收，所以在电脑端是 **下载/RX**。二者是同一条数据流的不同视角。

接收程序不能将完整备份读入内存，也不能经过文本编码转换。备份数据只走标准输出，错误和状态走标准错误，禁止使用 `2>&1` 将日志混入备份二进制流。Windows 端应使用二进制文件写入，避免旧版 PowerShell 文本重定向损坏内容。

## 3. 环境参数与敏感信息边界

实施时在个人受控环境维护以下参数，不将实际值填写进可分享的方案文档：

| 占位符 | 含义 |
|---|---|
| `<SSH_HOST>` | SSH 主机名或地址 |
| `<SSH_PORT>` | SSH 服务端口 |
| `<SSH_USER>` | 有权操作备份容器的系统账号 |
| `<SSH_PRIVATE_KEY_FILE>` | 本地私钥文件路径，不是私钥正文 |
| `<MYSQL_CONTAINER>` | 线上 MySQL 容器名 |
| `<MYSQL_PORT>` | 备份容器访问 MySQL 时使用的实际端口 |
| `<MYSQL_DATA_DIR>` | 宿主机 MySQL 数据目录 |
| `<MYSQL_CONFIG_FILE>` | MySQL 主配置文件 |
| `<MYSQL_INCLUDE_DIR>` | 配置引用的附加目录，可能不止一个 |
| `<DATA_MOUNT>` / `<DATA_DEVICE>` | 数据盘挂载点 / 底层块设备 |
| `<DEVICE_MAJOR_MINOR>` | 当次检测得到的设备主次编号，不跨机器照抄 |
| `<PXB_IMAGE_DIGEST>` | 已验证的 XtraBackup 镜像不可变引用 |
| `<LOCAL_BACKUP_ROOT>` | 本地备份根目录 |
| `<RUN_ID>` | 每次任务唯一编号 |
| `<RESTORE_DIR>` | 隔离环境的新恢复目录 |

认证分为两层：

1. SSH 密钥用于登录服务器；用户选择私钥文件，不粘贴长密钥文本。只有私钥本身设置了解锁口令才需要该口令。GUI SSH 软件保存的密钥不一定能被系统 OpenSSH 直接复用。
2. 数据库凭据用于 XtraBackup 登录 MySQL；它与 SSH 密钥和口令无关。优先专用备份账号，权限按工具官方说明授予，不必授予业务表写权限。使用已有管理员账号时，应控制凭据文件访问范围。

凭据通过交互输入或受控凭据机制提供。服务器凭据文件限制为仅所属用户可读写，所在目录限制访问；不将密码放在命令行、日志、源码、截图或分享文档中。

首次 SSH 连接须在已有可信渠道核对公开主机指纹。扫描到主机公钥不等于证明它可信；不能为了省事关闭主机校验。身份变化应拒绝并核查。不同 Windows OpenSSH 扫描工具可能存在算法兼容问题，应使用兼容版本，不降低认证要求。

## 4. 首次准备与只读检查

### 4.1 数据库信息

在数据库客户端执行：

```sql
SELECT VERSION(), @@datadir, @@port;

SELECT ENGINE, COUNT(*) AS table_count
FROM information_schema.tables
WHERE table_schema NOT IN ('mysql','sys','performance_schema','information_schema')
  AND table_type = 'BASE TABLE'
GROUP BY ENGINE;

SELECT COUNT(*) AS encrypted_tablespace_count
FROM information_schema.INNODB_TABLESPACES
WHERE ENCRYPTION = 'Y';

SHOW GLOBAL VARIABLES WHERE Variable_name IN (
  'innodb_page_size','lower_case_table_names',
  'innodb_data_home_dir','innodb_data_file_path',
  'innodb_undo_directory','innodb_directories',
  'innodb_redo_log_capacity','log_bin','time_zone'
);
```

仅在自己的运维环境保存结果，不把实际端口和业务信息回填本文。无加密表空间不代表所有日志、插件都必然无加密，恢复前仍应核对密钥管理与日志加密设置。加密实例必须配套备份恢复所需的密钥材料，并单独保护。

### 4.2 服务器、磁盘和容器

在 Linux SSH 终端核对系统、CPU 架构、数据目录真实挂载位置、空闲空间及配置包含目录。以下均为模板：

```bash
cat /etc/os-release
uname -m
df -h
docker inspect '<MYSQL_CONTAINER>' --format '{{range .Mounts}}{{println .Type .Source "->" .Destination}}{{end}}'
findmnt -nr -o TARGET,SOURCE,FSTYPE,MAJ:MIN -T '<DATA_MOUNT>'
docker info --format '{{.CgroupVersion}} {{.CgroupDriver}}'
stat -fc %T /sys/fs/cgroup
cat /sys/fs/cgroup/cgroup.controllers
```

目标环境应具备 cgroup v2、可用的 `io` 控制器及可定位的数据设备。还要检查备份容器实际的 `io.max`，不能只看根控制器列表就认定可用。

数据库目录大小与整个数据盘占用不同；盘内还可能有其他服务数据、日志和镜像。容量估算不得将整盘占用直接当作备份大小。`du` 的分配空间与数据文件逻辑长度也可能不同。

### 4.3 配置挂载检查

MySQL 主配置可能引用 `!include` / `!includedir`。这些路径在生产容器存在，不代表备份镜像中也存在。

- 将实际需要的主配置和包含目录映射到备份容器预期位置，保持只读。
- 包含目录有内容时一并处理，不能通过删除 include 指令、忽略错误来掩盖缺失配置。
- 启动前以实际挂载配置运行 XtraBackup 配置解析/版本检查；通过后才进入数据备份。
- 核对数据目录、独立表空间、Undo 及其他外置文件路径；发现额外存储位置要补充完整映射。

读取数据库凭据和配置解析通过只证明基本准备完成，不等于完整热备或恢复已经验证成功。

## 5. 压缩与资源限制

以下是初始参考值，不是所有服务器的固定最佳配置：

| 项目 | 初始参考 | 说明 |
|---|---|---|
| 数据盘读取上限 | 20 MB/s | 运行中可逐级加减，应先验证动态限速 |
| 读取线程 | 1 | 降低并发读取压力；并行度变更留到下次任务 |
| 压缩线程 | 1 | 压缩瓶颈需结合 CPU 实测判断 |
| 压缩算法 | ZSTD level 1 | 无损压缩，优先较低 CPU 开销 |
| 备份容器 CPU | 1 核配额 | 上限，不是独占保留一核 |
| 备份容器内存 | 4 GiB 上限 | 不提前分配；不足可能导致备份容器退出 |
| 备份容器交换空间 | 禁用额外 swap | Docker 可将 memory-swap 与 memory 设为相同值 |

不能把“有限额”理解为“生产不会受影响”。磁盘和网络仍与业务共享，SSH 加密、摘要计算及辅助进程的消耗也不完全包含在备份容器限额内。

确认整机内存余量应主要看 `available`，不是只看 `free`；不能简单把所有容器显示的内存上限相加。长期高负载时，应优先考虑从库或专用备份节点。

ZSTD 不会改变数据内容，但压缩率随文本、索引、重复内容和已有压缩数据而变。压缩是节省空间，不是加密；硬盘里仍包含业务数据，应做好访问控制。

## 6. 动态读取限速设计

### 6.1 为什么不依赖 XtraBackup 固定 throttle

在启动参数中把 XtraBackup 内部读取上限锁死，后续提高外层限速也无法突破内部上限。为了支持不中断调速，本方案让**外层 cgroup 控制实际磁盘读取上限**，XtraBackup 不再使用较低的固定内部 throttle。

必须先确保外层限制有效，再放开内部限制。不能只设置 `--throttle=0` 就直接无保护运行。

### 6.2 初始限制与在线修改

1. 查询实际数据盘设备及主次编号，定位专属备份容器的 cgroup。
2. 创建备份容器时就设置初始读取限制，例如 Docker 的 `--device-read-bps`，在备份进程执行前生效。
3. 启动后回读该容器 `io.max`，确认目标设备的 `rbps` 等于期望值；确认失败就停止本次备份。
4. 用户输入新速度时，只更新该备份容器、该设备的 `rbps`；保留其他控制项。
5. 再次回读确认后，更新界面和设置文件，写一条调速记录。

`io.max` 的概念格式如下，**不是可不经校验直接执行的生产命令**：

```text
<DEVICE_MAJOR_MINOR> rbps=<每秒允许读取的字节数>
```

例如 20 MB/s 对应 20,000,000 字节/秒。它限制物理块设备 I/O，允许短时突发；缓存读取、文件系统层次、日志读取等因素都会影响观测值，不能等同于“每秒处理多少逻辑数据库数据”。

必须校验容器唯一标签、容器 ID、进程 ID 与 cgroup 路径一致，防止误修改 MySQL 或整个宿主机的限制。设备编号不能硬编码到其他环境。

Docker 的 `update` 可修改 CPU 等资源，但不能假定它提供动态修改绝对磁盘读带宽的完整接口。本方案用经过校验的 cgroup `io.max`；更新 CPU 等 Docker 参数后，要重新核对/恢复当前读取限制，防止运行时重新应用旧配置。

### 6.3 实施前实测

使用独立测试容器和普通测试文件，不读业务表文件、不对裸盘做测试、不清空系统页缓存：

1. 在实际数据盘的独立临时目录准备约 256 MiB 测试文件，创建过程也限制写入速度。
2. 使用 direct I/O 持续读取该文件，降低缓存对结果的干扰。
3. 同一读取进程保持运行，调整上限 **10 → 20 → 10 MB/s**。
4. 分别采样 20～30 秒，按该 cgroup 的 `io.stat` 字节差除以实际时间，确认读取速率跟随变化。
5. 同时确认生产容器资源限制未变化；退出后清理测试容器和临时文件。

这项测试会产生有限磁盘负载，应在低峰进行。它只验证限速机制，不证明正式备份对业务无影响。

### 6.4 用户调速流程

```text
开始：20 MB/s
→ 观察业务、磁盘延迟、日志捕获情况
→ 正常则调整为 25 或 30 MB/s
→ 再观察 5～10 分钟
→ 有压力则降回原值；明显影响业务则停止备份
```

每次建议加 5～10 MB/s；实际允许范围按环境设定，例如工具可以限制在 5～80 MB/s，范围上限不是安全速度承诺。

调速不重启进程、不关闭数据流，已完成进度保留；读取线程数、压缩线程数等启动参数不必强求热修改。过度降低读取限速也可能拖慢 redo 捕获，不能用接近零的速度模拟无限暂停。

## 7. 备份执行与文件组织

### 7.1 单入口菜单

为减少误操作，可把服务端辅助脚本内置到本地单一入口，提供：

| 菜单 | 功能 |
|---|---|
| 配置连接 | 选择私钥、核对主机身份、上传工具、验证数据库凭据和配置 |
| 开始备份 | 创建唯一任务，设置初始资源限制，再开始传输 |
| 查看进度 | 查看状态、接收速度、空间和当前处理项 |
| 动态调速 | 调整当前任务读取上限，或单独调整 CPU |
| 停止任务 | 只停止该备份，不停止生产 MySQL |
| 重新校验 | 对已有完整文件重新计算摘要，无需访问源库 |

配置与真正开始备份必须分开，不能用户一配置完成就自动开始多 TB 读取。更新工具后先重新配置/检查，确保运行的是匹配版本。

### 7.2 推荐目录

```text
<LOCAL_BACKUP_ROOT>/
  启动入口
  操作说明.md
  备份设置.json             受控连接参数和限额，不存密码
  备份进度.txt              当前任务中文状态
  数据备份/
    <RUN_ID>.xbstream       已完整传输的数据库物理备份
  运行日志/
    备份记录.log            每小时和状态变化的历史
    工具异常.log            控制台或本地程序异常
    <RUN_ID>/
      full.xbstream.partial 尚未传完，成功后同盘移动到数据备份
      backup.log            原始备份日志
      progress.json         机器可读进度
      manifest.json         文件名、大小、摘要及版本信息
      SHA256SUMS.txt        文件校验清单
      备份结果说明.txt       中文结果与恢复位置
      TRANSFER_OK.txt       传输成功标志
      FILE_VERIFY_OK.txt    硬盘文件复核成功标志
```

“数据备份”仅放正式数据文件；失败文件与日志隔离。`.partial` 可能被操作系统显示为“部分下载”或浏览器图标，那只是扩展名关联，不改变内容。

相同文件系统内成功改名移动通常不需要再复制一整份，也不需要额外一倍数据空间。不能跨盘移动后仍假定成本相同。

日志和恢复元数据应与对应数据文件一起保管；归档时可以统一打包整个任务记录，但不能只留数据库大文件而丢掉恢复定位信息。

### 7.3 正确的成功判定

依次检查：

1. 远端 XtraBackup 退出码为 0，并报告正常完成。
2. SSH 传输及管道各环节退出正常，不能只检查最后一个进程的退出码。
3. 源端对发送的原始字节流计算 SHA-256，与本地接收时计算的摘要相同。
4. 刷新落盘后，将 `.partial` 改名为正式文件并保存清单。
5. 再从本地硬盘重新读取正式文件，核对大小和 SHA-256。
6. 在隔离环境恢复，确认 MySQL 可以启动并验证业务数据。

**传输成功 ≠ 文件复核成功 ≠ 实际恢复验证成功。** 状态文件应明确标注当前完成到哪一级。

后台 SSH 不能抢占菜单输入；二进制流不能连到交互终端。错误退出要保留窗口、中文原因和原始日志，不得静默退出或自动重复启动全量备份。

## 8. 数据一致性与备份时间点

热备中的数据文件不是同时复制的。XtraBackup 一边复制数据页，一边持续收集 redo；恢复前的 `prepare` 应用所需日志，并回滚未提交事务，形成同一恢复位置的一致数据库状态。

例：先复制的表后来又更新了，后复制的表已有较新的数据。只复制文件会留下混合时刻状态；加入本次收集的日志并正确 prepare 后，才整理成一致状态。因此“开始复制一张表的时间”不等于“该表最终恢复的时间”。

区分四个记录：

| 记录 | 用途 |
|---|---|
| 工具开始时间 | 本次备份作业的起点 |
| 工具结束时间 | 收尾完成的时间参考，不单独定义精确事务边界 |
| LSN、binlog/GTID 位置 | 工具记录的准确恢复坐标 |
| 本地接收/校验结束时间 | 传输和校验完成时刻，不是源库数据截止点 |

`xtrabackup_info`、`xtrabackup_checkpoints` 及存在时的 `xtrabackup_binlog_info` 必须保留。流式模式可以用 `--extra-lsndir` 另存信息和检查点副本，便于在大文件之外生成结果报告。

元数据解析应使用字段白名单，避免把包含口令的调用参数、完整敏感配置复制到报告里。统一时区并明确标注，保留原始时间及来源，不把服务器本地时间误认为 UTC。

未启用 binlog 的实例不能凭空生成 binlog 坐标；报告应明确“未启用，以 LSN 和工具元数据记录本次恢复位置”。不能仅凭全量备份任意恢复到更晚时间；要实现后续时间点恢复，需提前连续保存相应 binlog。不要为临时备份擅自改变生产日志配置。

## 9. 进度与运行监控

### 9.1 备份程序进度

中文进度文件建议每分钟覆盖一次，历史记录每小时追加；开始、调速、停止、失败、完成时立即记录。

至少显示：

- 任务编号、运行阶段、开始时间、最近更新时间。
- 已接收压缩字节数、最近采样速度、累计平均速度、运行时长。
- 当前处理项、最后收到数据的时间、移动硬盘剩余空间。
- 设置的读取上限、限速回读结果、CPU/内存限制。
- 收尾后记录恢复坐标；运行中显示“尚未确定”。

压缩后的总大小未知时不伪造百分比。重新读取一个完整文件做校验时，总大小已知，可以显示校验百分比。文件仍被打开时，资源管理器显示的大小/修改时间可能滞后，应以接收程序计数和任务日志为准。

### 9.2 MySQL 性能观察

在备份前收集 5～10 分钟基线；开始后前 10～15 分钟重点观察，再定期采样。以下查询只读，不扫描业务大表：

```sql
SELECT NOW() AS observed_at;
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Uptime','Threads_running','Threads_connected','Slow_queries',
  'Innodb_row_lock_current_waits','Innodb_row_lock_waits',
  'Innodb_log_waits','Innodb_buffer_pool_wait_free',
  'Innodb_data_pending_reads','Innodb_data_pending_writes'
);
```

| 指标 | 解释 |
|---|---|
| Threads_running | 当前未休眠线程，不等于都在使用 CPU |
| Threads_connected | 已建立连接数，不等于正在执行 SQL 的数量 |
| Innodb_row_lock_current_waits | 当前行锁等待数，观察是否持续积压 |
| Innodb_data_pending_reads/writes | 当前未完成的 I/O 请求 |
| Slow_queries | 累计慢查询数量，比较相同时间间隔的新增量 |
| Innodb_row_lock_waits | 累计行锁等待次数，比较新增量 |
| Innodb_log_waits | 累计日志缓冲区不足而等待刷出的次数 |
| Innodb_buffer_pool_wait_free | 累计等待可用缓冲页次数 |

实例重启或计数器重置后不能跨边界计算差值。慢查询计数受阈值配置影响，不增加也不代表业务完全没变慢。业务响应时间、写入延迟和错误率必须一起观察。

### 9.3 Linux 与容器观察

这些命令在实际数据库服务器的 SSH 终端运行，不在本地 Windows 或其他中转机运行：

```bash
docker stats
free -h -s 5
vmstat -S M 5
iostat -xz 5
```

分别开窗口执行，Ctrl+C 只退出这些监控。没有安装 `iostat` 时可先使用已有工具，不强制在备份途中安装依赖。

| 工具 / 字段 | 重点 |
|---|---|
| docker stats：CPU % | 约 100% 相当于一核，不代表整台多核机器满载 |
| MEM USAGE / LIMIT | 已用 / 上限，右边不是剩余内存 |
| NET I/O | 累计收 / 发流量，不是每秒网速 |
| BLOCK I/O | 累计磁盘读 / 写量，不是数据库大小 |
| PIDS | 进程和线程数，不是 MySQL 连接数 |
| free：available | 估计可供程序使用的内存，比单看 free 更有意义 |
| vmstat：id、wa | CPU 空闲比例、I/O 等待比例 |
| vmstat：r、b | 可运行任务数、不可中断等待任务数 |
| vmstat：si、so | 持续换页可能表明内存压力 |
| iostat：r_await、w_await | 读写延迟，单位毫秒，与备份前比较 |
| iostat：aqu-sz | 平均 I/O 队列长度，与延迟和业务表现结合观察 |
| iostat：%util | 设备繁忙时间比例；NVMe 多队列不能只凭此列判断饱和 |

`vmstat` 和 `iostat` 默认第一轮有开机累计/平均值，应看后续采样。`vmstat -S M` 将内存列改为 MiB，不把所有列都改成 MB；CPU 列仍为百分比，块设备吞吐另有单位。

不要因为备份进度在增长，就判定生产健康。业务已出现超时、写入失败应优先停止备份；轻微但持续的退化，可逐步降速并观察。阈值应基于业务基线，不能给所有系统套用固定 CPU 百分比。

## 10. 网络、压缩大小与时间估算

必须区分三个量：

1. 原始逻辑数据处理速度。
2. cgroup 控制的磁盘物理读取速率。
3. 压缩后通过网络到达本地的速度。

比如原始数据处理较快、压缩效果较好，本地每秒收到的数据可能明显少于读取上限；这不证明机械硬盘或公网只能达到该速度。CPU 配额、网络链路、磁盘等待和缓存也会影响结果。

服务器网卡总上传包含其他业务。购买的出口上限减去当前总上传量，只能估算理论余量，不是两端实测可用带宽。网卡显示的链路速率也不等同于购买的公网出口。避免在生产高峰跑满带宽的测速。

单位关系：1 MB = 1,000,000 字节；1 MiB = 1,048,576 字节；1 MiB/s 约等于 8.39 Mbps。

```text
压缩比例 = 压缩后大小 / 实际对应的原始大小
传输时间估计 = 预计压缩总量 / 长期平均接收速度
原始读取时间估计 = 需要读取的实际数据量 / 实际处理速度
```

读取、压缩、传输是流水线，不把三段时间简单相加，慢的一环往往主导总时间；最后的硬盘复核另计。

**配置的读取上限不是实测读取量。** 不能仅凭“限速 20 MB/s、接收 4 MB/s”断言压缩率正好 20%，也不能把某张文本大表的早期样本直接套用全库。

只根据现有进度估算时，应列出假设和范围。需要更精确结果，可在获得授权后使用有代表性的同算法样本，或记录实际源端处理量；不能为了估算擅自额外读取生产大表、重压缩整库或扫描移动硬盘。

## 11. 停止、失败与空间清理

### 11.1 动态调速不等于暂停续传

在线修改读取上限，备份进程和日志捕获仍在工作，任务连续性得以保留。

完全终止后，源库继续变化；不能重启进程后简单往旧文件追加，也不能只凭已经下载多少字节恢复现场。不要通过冻结容器、停止日志读取来模拟长时间暂停。

若必须支持分天下载、任意中断续传，需要先在独立存储形成完整备份，再下载固定文件，或基于经过验证的一致性快照/副本设计另一个方案。这需要额外存储能力，不是给当前流式脚本加一个按钮即可实现。

### 11.2 安全停止

- 首选本地菜单的停止动作：停止接收，发送只针对当前唯一任务的远端停止请求。
- 校验容器 ID 和任务标签后，只停止独立备份容器，不停止 MySQL、不停止整个 Docker。
- 停止需等待进程退出、连接断开和资源释放，不承诺按下按钮就瞬间无负载。
- 网络异常时从已建立的可信 SSH 会话检查任务容器；不要仅根据电脑窗口消失推断服务器已经停止。
- 只中断“完整传输后的本地复核”，可重新执行复核，不必重新生成备份。

备份容器只读挂载数据目录，正常停止不会删除线上数据或撤销业务事务；本次未完成副本无效。备份持有的锁随连接退出释放，但已提交 I/O 和队列可能仍需短暂时间排空。

### 11.3 清理规则

清理前必须同时确认：任务已停止、本地没有写入、服务器备份容器已退出、没有成功标记、路径确实属于该次任务。

仅删除明确无用的 `.partial` 和该次不再需要的临时数据；保留错误原因和必要记录。不要使用未经核对的递归通配删除，不删除成功备份，不删除连接配置或数据库源目录。

每次任务使用新目录和唯一文件名，拒绝覆盖已有结果。移动硬盘空间保护、服务器系统盘和数据盘空间保护都应启用；保护阈值是兜底，不能替代容量预估与增长监控。

### 11.4 常见故障

| 现象 | 优先检查 | 处理原则 |
|---|---|---|
| 指纹扫描失败 | SSH 地址/端口、算法兼容性 | 使用兼容工具；不关闭主机身份校验 |
| 密钥认证失败 | 是否选了公钥、格式是否支持、代理是否可用 | 选择正确私钥；不把私钥内容发送给他人 |
| `includedir` 目录不存在 | 备份镜像缺少生产配置引用的目录 | 完整映射包含目录并先做配置解析检查 |
| 进度为零、工具退出 | 原始日志、配置、权限 | 零字节不等于初始化完成；先修复，不反复盲重试 |
| 窗口突然关闭 | 异常日志、后台 SSH 是否占用输入 | 留屏、记录异常、确认远端状态后处理 |
| redo 跟不上/被覆盖 | 日志生成速率、限速、网络背压、CPU | 失败备份不能使用；评估参数，不忽略一致性错误 |
| 内存上限触发退出 | 备份容器内存与 OOM 状态 | 只在确认整机余量后调整，不能取消限制冒险 |
| 限速回读失败 | 控制器、设备、cgroup 路径、权限 | 停止任务，不降级成无限速运行 |
| 校验不一致 | 传输退出码、磁盘错误、二进制管道 | 保留失败标记和日志，不认定成功 |

注册 redo consumer 等机制可能改变日志保留与写入等待行为，不能作为“修复慢网络”的通用开关随意开启。也不要擅自扩大 redo、关闭刷盘或修改生产持久性参数来迁就备份。

## 12. Linux 恢复流程

### 12.1 恢复前提

在隔离 Linux 环境恢复，优先使用与源端相同的 MySQL 准确版本、CPU 架构及本次 XtraBackup 镜像。记录并匹配必要初始化参数、插件、页大小、大小写规则和密钥管理配置。

准备足够空间容纳解压后的实际数据，以及日志、临时空间和余量。保存压缩包的磁盘不一定还能同时容纳完整解压数据；仅有少量本地空闲空间、即使安装了 MySQL，也不能完成多 TB 实例恢复。

这不是往现有数据库中导入 SQL。目标实例必须停止、目标数据目录为空，或使用全新隔离实例目录。不能直接覆盖正在运行的 MySQL，也不能把 Linux 物理数据包直接塞进现有 Windows MySQL 数据目录。

### 12.2 校验与解包

先比较备份清单、原始日志和正式文件，确认任务成功；重新计算摘要并与源端记录比较：

```bash
sha256sum '<BACKUP_ARCHIVE_FILE>'
```

确认一致后，设置实际恢复路径和已验证镜像。以下命令仅在隔离恢复机器执行；`<RESTORE_DIR>` 应为全新目录，若已存在，先人工检查，不应直接复用：

```bash
restore_image='<PXB_IMAGE_DIGEST>'
restore_archive='<BACKUP_ARCHIVE_FILE>'
restore_dir='<RESTORE_DIR>'
mkdir "$restore_dir"

docker run --rm -i --user 0:0 \
  --mount "type=bind,source=$restore_dir,target=/restore" \
  --entrypoint xbstream "$restore_image" \
  -x --decompress --decompress-threads=2 -C /restore \
  < "$restore_archive"
```

镜像应提前准备好并核对 digest。解包同时解压可避免在恢复盘再放一份完整压缩目录；原始备份文件继续保留。

### 12.3 prepare 整理一致性

上一步成功退出后执行：

```bash
docker run --rm --user 0:0 \
  --mount "type=bind,source=$restore_dir,target=/restore" \
  --entrypoint xtrabackup "$restore_image" \
  --prepare --use-memory=1G --target-dir=/restore
```

`--use-memory` 是恢复准备阶段参数，按恢复机容量选择；它不等于线上备份容器内存上限。必须检查退出码及工具成功完成信息；不能遇到错误后直接尝试启动数据库。

核对解包得到的 `xtrabackup_info`、`xtrabackup_checkpoints` 以及存在时的 binlog 元数据，确认恢复位置和预期任务一致。

### 12.4 启动隔离实例并验收

可以直接将准备好的目录作为新 MySQL 实例的数据目录，避免再复制一份；或使用 `--copy-back` 到另一个空目录，但要考虑额外空间。

启动前：

1. 为恢复目录设置目标 MySQL 运行用户需要的权限，不能误改源库目录。
2. 匹配 `lower_case_table_names`、`innodb_page_size` 等要求，勿凭默认值猜测。
3. 校验原部署所需插件与额外路径；原始配置不能未经适配直接套到新机器。
4. 使用隔离网络和独立实例标识，不让业务应用自动连接。
5. 禁止复制线程、事件调度等自动访问生产或执行业务动作，直到验证明确需要。

验证清单：

- MySQL 正常启动，错误日志没有未解决的恢复失败。
- 关键库表、用户权限和必要对象存在。
- 检查代表性业务记录、跨表关联及截止位置附近的数据。
- 大表先做有索引的抽样，不上来就反复全表 COUNT。
- 验证实际业务查询，记录恢复耗时和额外所需空间。

最后生成独立的恢复演练记录，标明“已恢复验证”及范围。文件摘要通过但未执行上述步骤时，只能称“文件完整性已验证”。

## 13. 后续复用清单

### 每次开始前

- 确认服务器、数据库实例和磁盘路径，不能误连中转机或其他环境。
- 确认没有重复运行的备份，连接设置与当前工具版本匹配。
- 检查服务器和移动盘余量、电脑休眠/重启计划、网络及硬盘连接。
- 保存正常业务基线，避开改表结构、批量导入等高负载时段。
- 初始限速已设置；设备/cgroup 变更或换机器后重新验证。

### 运行中

- 看业务延迟和错误率，再看 CPU、I/O、内存及备份日志。
- 逐级加速、记录每次调整；只调上限，不承诺实际速度达标。
- 观察最后收到数据的时间、磁盘增长、redo 追赶情况。
- 发生业务异常先止损，确认停止结果后再考虑重新备份。

### 完成后

- 确认源端、SSH、摘要和落盘复核各层成功。
- 保存数据、报告、清单和必要恢复材料，避免记录混淆。
- 在独立环境做恢复验证。
- 清理该次服务器临时资源；需要轮换旧备份时先确认保留策略，不自动删唯一副本。

### 长期改进

频繁备份或恢复时间要求较高时，评估专用从库、独立备份存储、已验证的增量链和持续 binlog 归档。增量备份需要完整、可用的基线，不能用来补齐一次已经中断的首次全量备份。
