# Elasticsearch 大数据量索引与蓝绿迁移通用方案

> 文档定位：面向可重放权威数据源的大规模 Elasticsearch 索引设计、全量回灌、增量追平、在线扩容、故障重建与蓝绿迁移。
>
> 示例约定：本文中的索引名、表名、字段名、时间边界、容量阈值和数据量均为通用示例，不对应任何特定项目、组织、业务或生产环境。落地时必须结合真实版本、数据样本、查询模型、硬件和恢复目标重新验证。

## 1. 核心结论

一套可长期维护的 Elasticsearch 迁移方案，重点不是把旧索引复制到新集群，而是建立以下闭环：

1. 业务数据库或其他可重放数据源是权威来源，Elasticsearch 是可重建的检索投影。
2. 业务时间负责决定文档属于哪个分区，同步游标只负责发现哪些来源记录尚未处理，两者不能混用。
3. 全量、增量、失败重试和故障重建必须共用稳定文档 ID、时间路由、字段转换和来源优先级规则。
4. 大索引使用可预测的固定时间分区；稀疏旧数据可合并为历史归档；异常时间进入独立隔离分区。
5. 应用只读写稳定别名，不保存或拼接当前物理索引名。换代、扩容和重建都通过原子别名切换完成。
6. 全量任务先固化 T0 上界，再用主键或复合游标扫描；增量从 T0 前的安全重叠区开始，依靠稳定 ID 幂等收敛。
7. Bulk 中任一项目失败，本批安全断点都不能前移。断点表示“已完整提交的来源位置”，不表示 ES 文档数。
8. Split 用于容量扩容，Reindex 用于不满足 Split 前提时的兼容迁移，故障重建则从权威数据源恢复，三者不能混为一谈。
9. 数据校验应比较业务唯一键去重数、分区内按时间分布和字段样本，不能简单比较来源行数与 ES 文档数。
10. `0` 副本只适用于明确接受重建时间、权威来源完整且查询禁止部分结果的场景；否则应保留副本和快照。

## 2. 适用范围与选型边界

### 2.1 适合使用本方案的场景

- 来源数据可按稳定游标重复读取，历史数据仍然完整。
- 查询大多携带时间范围，且存在明显的冷热分布。
- 数据可能晚到或补录，要求相同业务时间始终落到同一分区。
- 需要在不停止旧集群服务的情况下构建新集群并灰度切换。
- 需要通过重建或 Mapping 升级产生新一代物理索引。
- 文档可能来自多个数据源，需要确定性去重和优先级合并。

### 2.2 不应直接套用的场景

- 纯日志、指标等严格按写入时间追加的数据，且没有历史补录：优先评估 Data Stream、ILM 和标准 rollover。
- 权威来源会删除历史数据且没有快照：不能承诺 ES 可完整重建。
- 查询几乎不带时间范围：过细时间分区可能放大 fan-out，应优先调整查询契约或采用其他分区方式。
- 来源更新没有 `updated_at`、CDC 或变更日志：仅靠 `id > lastId` 无法发现旧行更新。
- 业务时间或稳定 ID 组成字段会修改：必须设计旧分区删除与新分区写入的搬迁协议。

## 3. 总体架构

```text
                         +-----------------------+
                         |  同步任务元数据       |
                         |  es_sync_task         |
                         +-----------+-----------+
                                     |
+----------------+       +-----------v-----------+       +------------------+
| 权威数据源     +-------> 确定性规则核心        +-------> Elasticsearch    |
| 主库/只读库/CDC|       | ID/路由/转换/优先级   |       | 新集群           |
+----------------+       +-----+-------------+---+       +---------+--------+
                              |             |                       |
                    +---------v---+   +-----v-------+       +-------v---------+
                    | 全量导入器  |   | 在线增量器  |       | 分区元数据      |
                    | 重建/校验   |   | 定时或 CDC  |       | es_index_partition|
                    +-------------+   +-------------+       +-------+---------+
                                                                  |
                                                        +---------v---------+
                                                        | 查询目标解析器    |
                                                        | 别名+精确时间过滤 |
                                                        +-------------------+
```

建议拆出一个不依赖 Web、调度框架和运行环境的“确定性规则核心”，至少包含：

- 文档 ID 生成与版本管理。
- 业务时间标准化与分区路由。
- 来源记录到 ES 文档的转换。
- 多来源规范记录选择与字段优先级。
- Mapping 版本、路由版本和索引命名规则。
- 幂等合并脚本或更新请求构造。

全量导入器和在线增量器都依赖这套核心规则。只在两处“写出相似逻辑”仍然会产生漂移，最终表现为重复文档、跨分区错写或重试结果不一致。

## 4. 索引与分区设计

### 4.1 先按负载类型分类

| 负载类型 | 典型特征 | 推荐结构 |
| --- | --- | --- |
| A：高吞吐文本事件 | 数据量大、按时间查询、存在历史补录 | 历史归档 + 固定短时间分区 |
| B：大字段媒体文本 | 单文档大、容量增长不易预估 | 历史归档 + 固定短时间分区 + 按最大主分片自动扩容 |
| C：中低吞吐元数据 | 文档小、增长较慢、查询范围较宽 | 历史归档 + 月度或季度分区 + 时间异常隔离索引 |
| D：小型维度或字典 | 总量可控、经常全局查询 | 固定索引，达到容量或查询瓶颈后再拆分 |

不同逻辑索引可以采用不同归档边界和分区粒度，不要为了“统一”强迫所有数据使用同一种周期。

### 4.2 分区粒度由三个约束共同决定

1. 查询窗口：常见查询应只命中少量分区。
2. 恢复时间目标：单个物理索引损坏时，可接受重建多长时间范围的数据。
3. 主分片容量：每个主分片应落在经过压测确认的目标区间内。

主分片数可用下式做初步估算：

```text
primary_shards = ceil(estimated_primary_store_bytes / target_shard_bytes)
```

例如目标单主分片约 `30 GiB`，一个固定时间区间预计主数据约 `82 GiB`，可以从 `3` 个主分片起步。`20-40 GiB` 只是常见起始参考，不是 Elasticsearch 的硬限制；最终值应结合查询延迟、Merge、恢复速度、Heap、磁盘和节点数量压测确定。

不要为了得到精确分片数，先在超大来源表上执行整月 `COUNT(*)`。更稳妥的方式是：

- 使用最终 Mapping 和代表性样本试灌。
- 记录每百万去重文档的主存储大小。
- 按近期高峰增长率估算未来分区。
- 写入后持续观察最大主分片，而不是只看索引总大小。

### 4.3 固定短时间分区

当查询默认窗口约为一周、又希望把单次故障重建限制在一周左右时，可以采用月内固定四段：

```text
01-08
09-16
17-24
25-月末
```

所有边界使用明确业务时区和左闭右开区间。文档无论何时到达，都根据业务时间计算唯一目标区间，不能根据“当前哪个索引未写满”决定目标。

固定时间分区相对纯容量 rollover 的优势是：

- 历史补录可以确定性路由。
- 查询目标可以根据时间范围提前计算。
- 故障重建范围明确。
- 同一业务时间不会因到达顺序不同落入多个索引。

代价是需要维护分区元数据，并对空分区、跨区查询和晚到更新做明确处理。

### 4.4 历史归档

早期数据如果稀疏，可以在某个 `<archive_boundary>` 之前合并成一个历史归档物理索引。归档仍只容纳同一个逻辑索引的数据，不能把不同文档结构混写。

归档的收益：减少小索引和小分片数量。

归档的代价：

- 查询归档中的窄时间范围仍可能访问归档索引的全部主分片。
- 任一无副本主分片永久丢失时，需要重建完整归档范围。
- 归档越大，恢复时间越长。

因此归档边界应由实际数据密度、访问热度和可接受恢复时间决定，而不是照搬示例年份。

### 4.5 按需创建

只有第一次遇到某时间范围内的有效文档时，才创建分区记录、物理索引和别名。没有数据的归档、月份、短时间段或季度，不预建空索引。

必须区分两种状态：

- 没有分区元数据：该范围确认没有可查询数据，可以返回空结果。
- 已有分区元数据但索引、别名或主分片异常：这是故障，必须失败并告警，不能伪装成空结果。

### 4.6 异常时间隔离

来源数据可能包含明显超前或非法时间。若直接按原始时间创建分区，可能产生大量零散未来索引。

通用做法是：

1. 全量任务首次创建时固化 `time_reference`。
2. 计算并持久化 `future_boundary = time_reference + tolerance`。
3. 超过边界的记录写入唯一 `time-outlier` 分区。
4. 文档保留原始业务时间，并增加 `timeAnomaly`、`timeAnomalyType` 等标记。
5. 任务续跑和重试必须复用原边界，不能按当前时间重新计算。
6. 查询正常时间分区时额外加入异常分区别名，再用原始业务时间做精确过滤。

异常日期后来真正到达时，不应自动搬迁，除非系统已经实现可靠的“旧分区删除 + 新分区写入 + 幂等恢复”协议。

### 4.7 副本与快照决策

| 策略 | 优点 | 风险与前提 |
| --- | --- | --- |
| `replicas >= 1` | 节点故障可自动恢复，RTO 较短 | 需要额外磁盘和网络，仍不能替代备份 |
| `replicas = 0` | 节省接近一半索引存储 | 节点或磁盘永久故障会丢主分片，必须从权威来源重建完整物理索引 |
| Snapshot | 提供独立恢复路径，降低源库压力 | 需要仓库、保留策略和恢复演练 |

采用 `0` 副本前至少确认：

- 权威来源长期保留且可高效扫描。
- 每个分区的重建时间满足业务 RTO。
- 查询设置为不接受部分分片结果。
- 节点故障可能同时损坏多个分区时，集群和源库仍有足够恢复能力。
- 已书面接受无快照时的恢复边界。

## 5. 命名与别名体系

### 5.1 物理索引命名

建议格式：

```text
${logical_index}-v${schema_version}-${period_key}-p${sequence}-g${generation}
```

示例：

```text
event-search-v2-2026.08-p01-g000001
event-search-v2-archive-p01-g000002
asset-search-v2-time-outlier-p01-g000001
```

其中：

- `schema_version` 表示文档与 Mapping 大版本。
- `period_key` 表示归档、年月、季度或异常时间。
- `sequence` 表示周期内固定分区序号。
- `generation` 表示同一业务时间范围的物理代数，用于 Split、Reindex、重建或 Mapping 升级。

### 5.2 三层别名

```text
${logical_index}_read                         全局兼容读别名
${logical_index}_read-${period_key}           周期读别名
${logical_index}_partition-${partition_key}   稳定分区别名，可作为写入目标
```

约束：

- 一个稳定分区别名只指向一个当前有效物理索引，并设置 `is_write_index=true`。
- 周期读别名只包含该周期实际存在的当前代分区。
- 全局读别名只用于全历史或暂时缺少时间参数的兼容查询。
- 全量、增量和失败重放都写稳定分区别名，不写物理索引名。
- 同步任务不得保存一个会在换代后失效的物理索引名作为长期写入目标。

### 5.3 原子切换

新代校验通过后，在一次 `_aliases` 请求中同时切换全局读别名、周期读别名和稳定分区别名：

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "event-search-v2-2026.08-p01-g000001", "alias": "event-search_read" } },
    { "remove": { "index": "event-search-v2-2026.08-p01-g000001", "alias": "event-search_read-2026.08" } },
    { "remove": { "index": "event-search-v2-2026.08-p01-g000001", "alias": "event-search_partition-2026.08-p01" } },
    { "add": { "index": "event-search-v2-2026.08-p01-g000002", "alias": "event-search_read" } },
    { "add": { "index": "event-search-v2-2026.08-p01-g000002", "alias": "event-search_read-2026.08" } },
    { "add": { "index": "event-search-v2-2026.08-p01-g000002", "alias": "event-search_partition-2026.08-p01", "is_write_index": true } }
  ]
}
```

任何一个查询入口或写入口没有一起切换，都可能造成读写指向不同代。

## 6. 元数据模型

### 6.1 为什么需要两张表

```text
es_sync_task
一条记录 = 一个可续跑任务
记录：任务处理什么、固定上界、当前安全断点、状态和错误。

es_index_partition
一条记录 = 一个真实物理索引的一代
记录：负责的业务时间范围、别名、分片数、版本、状态和容量。
```

任务与物理索引不是一一对应关系。一个全量批次可能写入多个分区；一个分区也可能经历多次扩容或重建。

### 6.2 任务表参考 DDL

以下为 MySQL 示例，其他数据库可将 JSON 改为等价类型或 TEXT：

```sql
CREATE TABLE es_sync_task (
    id BIGINT NOT NULL AUTO_INCREMENT,
    task_code VARCHAR(96) NOT NULL,
    task_type VARCHAR(32) NOT NULL COMMENT 'FULL_IMPORT/INCREMENTAL/SPLIT/REINDEX/REBUILD/VERIFY',
    logical_index VARCHAR(64) NOT NULL,
    target_partition_id BIGINT DEFAULT NULL,
    source_name VARCHAR(96) NOT NULL,
    plan_version VARCHAR(32) NOT NULL,
    upper_bound_json JSON DEFAULT NULL,
    checkpoint_json JSON DEFAULT NULL,
    task_status VARCHAR(32) NOT NULL DEFAULT 'INIT',
    source_success_count BIGINT NOT NULL DEFAULT 0,
    document_success_count BIGINT NOT NULL DEFAULT 0,
    failure_count BIGINT NOT NULL DEFAULT 0,
    error_summary VARCHAR(1000) DEFAULT NULL,
    started_at DATETIME DEFAULT NULL,
    finished_at DATETIME DEFAULT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_task_code (task_code),
    KEY idx_task_lookup (logical_index, task_type, task_status),
    KEY idx_target_partition (target_partition_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`upper_bound_json` 保存首次创建后不能漂移的参数，例如：

```json
{
  "snapshotMaxId": 900000000,
  "sourceStartId": 0,
  "sourceEndId": 0,
  "timeReference": "2026-08-01T00:00:00+08:00",
  "futureBoundary": "2026-10-30T00:00:00+08:00",
  "routingVersion": "TIME_8D_V1",
  "mappingVersion": "event-v2.1"
}
```

`checkpoint_json` 只保存最后一个完整成功批次的位置：

```json
{ "lastId": 350000000 }
```

复合游标示例：

```json
{ "updatedAt": "2026-08-01T10:30:00+08:00", "lastId": 812345 }
```

### 6.3 分区表参考 DDL

```sql
CREATE TABLE es_index_partition (
    id BIGINT NOT NULL AUTO_INCREMENT,
    logical_index VARCHAR(64) NOT NULL,
    physical_index VARCHAR(160) NOT NULL,
    period_key VARCHAR(32) NOT NULL,
    sequence_no INT NOT NULL,
    generation_no INT NOT NULL DEFAULT 1,
    business_time_start DATETIME DEFAULT NULL,
    business_time_end DATETIME DEFAULT NULL,
    primary_shard_count INT NOT NULL,
    routing_version VARCHAR(32) NOT NULL,
    mapping_version VARCHAR(32) NOT NULL,
    read_alias VARCHAR(160) NOT NULL,
    write_alias VARCHAR(160) NOT NULL,
    source_cursor_min JSON DEFAULT NULL,
    source_cursor_max JSON DEFAULT NULL,
    document_count BIGINT NOT NULL DEFAULT 0,
    primary_store_bytes BIGINT NOT NULL DEFAULT 0,
    max_primary_shard_bytes BIGINT NOT NULL DEFAULT 0,
    partition_status VARCHAR(32) NOT NULL DEFAULT 'CREATING',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    retired_at DATETIME DEFAULT NULL,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_physical_index (physical_index),
    UNIQUE KEY uk_partition_generation
        (logical_index, period_key, sequence_no, generation_no),
    KEY idx_partition_lookup
        (logical_index, business_time_start, business_time_end, partition_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`source_cursor_min/max` 只用于观测和校验，不能代替分区的业务时间边界。晚到历史记录可能拥有很大的来源 ID，因此按来源 ID 猜测完整重建范围是不可靠的。

### 6.4 状态机

任务状态：

```text
INIT -> RUNNING -> SUCCESS
          |  |
          |  +-> FAILED -> RUNNING
          +----> PAUSED -> RUNNING
```

分区状态：

```text
CREATING -> WRITING -> SPLITTING/REBUILDING -> RETIRED -> DELETED
    |          |                |
    +----------+--------------> FAILED
```

状态只在外部动作已确认完成后推进。例如，只有确认旧物理索引确实删除成功，才能把旧代标记为 `DELETED`。

## 7. Mapping、字段与稳定文档 ID

### 7.1 Mapping 原则

- 使用版本化 Index Template 管理 Mapping、分析器和基础设置。
- 大型业务索引优先 `dynamic: strict`，避免意外字段导致映射膨胀。
- 精确查询、过滤、聚合和排序使用 `keyword`、数值或日期类型。
- 只展示、不查询的字段保留在 `_source`，设置 `index: false`；不聚合时同时关闭 `doc_values`。
- 只给真实参与全文检索的字段配置分析器。
- 不重复保存可推导字段、空占位字段、大块原始 JSON 和同义副本。
- `_id` 已经存在于命中元数据中，不需要在 `_source` 重复保存，除非下游导出协议明确需要。

### 7.2 分析器必须通过样本试灌

不要凭经验直接把所有文本字段配置成宽范围 n-gram。测试集至少应包含：

- 中文、英文、数字、符号和混合文本。
- 短词、长词、路径、文件名、多段扩展名。
- 大正文和高频短关键词。
- 业务真实查询词与必须避免的误召回样本。

每个候选分析器至少比较：召回率、误召回、索引主存储、写入吞吐、Merge 压力、查询 P95/P99 和高亮耗时。

### 7.3 稳定 ID

稳定 ID 应来自业务唯一键，而不是数据库自增主键、批次号或物理索引名。

避免简单字符串拼接产生歧义：

```text
错误："ab" + "c" 与 "a" + "bc" 可能得到同一输入
建议：版本号 + 长度前缀编码，或字段名固定的规范 JSON
```

参考算法：

```text
canonical = "id-v1|" +
            len(key1) + ":" + key1 + "|" +
            len(key2) + ":" + key2 + "|" +
            len(key3) + ":" + key3

document_id = SHA-256(UTF-8(canonical))
```

规范化规则一旦上线就要版本化。大小写、空白、路径分隔符、Unicode 归一化、时区和空值表示都必须显式定义；不能在某个同步入口中临时增加转换。

### 7.4 确定性合并

同一稳定 ID 可能对应多个来源记录。最终文档必须与处理顺序无关：

- 集合字段：去空、去重并按固定规则排序。
- 计数字段：由最终集合重新计算，不能累加重试次数。
- 公共字段冲突：明确选择最早来源、最新版本、最高优先级或其他稳定规则。
- 多来源正文：给来源定义数值优先级，低优先级更新不得覆盖高优先级内容。
- 规范来源选择：必须只依赖稳定业务字段，不能依赖哪个来源先到达。

存在并发合并时，使用 `update + upsert`、脚本化条件更新或外部版本控制，并配置适当的版本冲突重试。普通 `index` 整文档覆盖通常无法保证集合合并和来源优先级。

## 8. 业务时间路由与查询目标解析

### 8.1 业务时间与同步游标

| 概念 | 作用 | 典型字段 |
| --- | --- | --- |
| 业务时间 | 决定归档、月份、短分区或季度 | `eventTime`、`createdTime` |
| 同步游标 | 发现新增或更新来源记录 | `id`、`(updatedAt,id)`、CDC offset |
| 同步时间 | 观测延迟和任务运行时间 | `processedAt` |

禁止用同步时间、识别完成时间或数据库更新时间代替业务时间路由。晚到结果只能更新原业务时间分区中的同一文档。

所有环境使用配置中的明确业务时区，例如 `Asia/Shanghai`，不要依赖 `ZoneId.systemDefault()` 或操作系统默认时区。

### 8.2 写入路由伪代码

```text
route(logicalIndex, businessTime, taskBoundary):
    normalizedTime = normalizeToBusinessZone(businessTime)

    if normalizedTime is invalid:
        return INVALID_TIME_POLICY

    if taskBoundary exists and normalizedTime > taskBoundary.futureBoundary:
        return TIME_OUTLIER

    if normalizedTime < archiveBoundary(logicalIndex):
        return ARCHIVE

    return fixedPeriod(logicalIndex, normalizedTime)
```

路由结果应包含 `period_key`、`sequence_no`、左闭右开时间边界和 `routing_version`。写入时再从分区表解析当前 `write_alias`，不能由任务中的旧代数拼接物理索引名。

### 8.3 查询目标解析

查询流程：

1. 将请求时间转换为业务时区下的左闭右开范围。
2. 与归档边界求交，只在归档元数据存在时加入归档别名。
3. 从分区元数据查询所有实际存在且与范围相交的当前有效分区。
4. 小范围优先使用稳定分区别名，大范围可合并为周期读别名。
5. 有异常时间分区的逻辑索引，额外加入异常别名。
6. ES 查询中仍保留精确业务时间范围条件。
7. 分区元数据存在但索引或主分片异常时明确失败并告警。

别名只减少目标索引集合，不能代替文档级时间过滤。

### 8.4 查询契约

- 默认查询应有合理时间范围，只有用户明确选择全历史时才访问全局读别名。
- 不根据返回结果的 `_index` 精确名称判断业务类型；请求上下文应携带逻辑类型。
- 排序必须包含稳定且唯一的 tie-breaker，例如 `score DESC, eventTime DESC, businessKey ASC`。
- 深分页优先使用 `search_after` 和 PIT，限制 `from + size`。
- 设置 `allow_partial_search_results=false` 或等价保护，避免主分片失败时返回看似正常的残缺结果。

## 9. 全量回灌与增量追平

### 9.1 T0 快照上界

全量任务首次启动时记录来源的 T0 上界：

```sql
SELECT MAX(source_id) FROM source_record;
```

随后使用 keyset pagination：

```sql
SELECT ...
FROM source_record
WHERE source_id > :last_success_id
  AND source_id <= :snapshot_max_id
ORDER BY source_id
LIMIT :batch_size;
```

禁止在超大表上使用深 `OFFSET`。任务创建后，T0、来源范围、路由版本、Mapping 版本和异常时间边界都必须从任务表读取，修改本地配置不能改变未完成任务的含义。

### 9.2 全量与增量衔接

```text
记录 T0
  |-- 全量：处理 source_id <= T0
  `-- 增量：从 max(0, T0 - overlap) 开始，持续处理新数据
```

重叠区用于覆盖长事务、提交顺序和调度边界。重叠大小应根据来源写入速率和最长事务时间试算；稳定 ID 和确定性合并保证重复扫描不改变最终结果。

如果来源允许旧行更新，按能力选择：

| 来源能力 | 游标建议 | 注意事项 |
| --- | --- | --- |
| 只追加、自增 ID 且提交顺序可靠 | `id` | 仍建议安全重叠 |
| 允许更新且时间精度可靠 | `(updated_at, id)` | 使用复合排序，并回看小窗口 |
| 更新、删除、乱序提交复杂 | CDC offset | 需要处理 delete 和跨分区搬迁 |
| 无可靠更新时间或日志 | 无法保证 | 需要补字段、引入 CDC 或周期性校准 |

### 9.3 批次处理顺序

```text
读取来源批次
-> 批量读取关联数据
-> 构建规范记录和稳定 ID
-> 按稳定 ID 做批内合并
-> 按目标分区别名分组
-> 受控创建缺失分区
-> Bulk 写入
-> 检查每一个 Bulk item
-> 全部成功后提交任务断点
```

一个来源批次可能写入多个历史或当前分区。只有所有目标分区都成功，才能推进该来源批次的安全断点。

### 9.4 Bulk 控制

初始参考值：

```text
每批来源记录：2,000-5,000
单次 Bulk 实际请求体：5-15 MiB
每个逻辑索引并发：1 起步
```

大字段文档应优先按实际字节数动态拆批，不能只按记录数。出现 `429`、Bulk rejection、Merge 积压、磁盘延迟升高或查询 P95 明显恶化时，降低并发和批次大小，并采用带抖动的指数退避。

全量导入期间可以临时调大 `refresh_interval` 或设置为 `-1`，但正式校验和切流前必须恢复配置并执行 refresh。

### 9.5 失败与断点

- Bulk HTTP 成功不代表每个 item 成功，必须逐项检查。
- 任一 item 失败时，不推进整个批次断点，并按相同规则重试完整批次。
- 超过自动重试次数后将任务标记为 `FAILED`，保留原断点和错误摘要。
- 修复后从原安全断点继续，不能人工跳过失败范围。
- `source_success_count` 统计成功处理的来源行，`document_success_count` 统计写入动作，二者都不等于最终去重文档数。

### 9.6 调度与并发

一个调度入口可以顺序处理多条来源流，但每条来源流必须有独立任务记录和独立断点。某一来源失败，不能推进或覆盖另一来源的断点。

第一版如果只允许单实例执行，应通过部署约束、配置开关和进程内防重入明确保证。真正需要多实例抢占任务时，再增加数据库租约、心跳和乐观锁，不要假装单机状态机天然支持分布式并发。

## 10. 在线扩容：Split 与 Reindex

### 10.1 触发指标

扩容应观察“最大的单个主分片”，不能只看物理索引总大小。多主分片索引可能总量很大但分布健康，也可能因路由偏斜出现单个超大分片。

阈值必须来自压测。一个可用于试验的起点是：目标主分片 `20-40 GiB`，最大主分片达到约 `45 GiB` 时触发评估，而不是直接视为通用生产标准。

### 10.2 Split 前提

- 创建源索引时预留足够的 `number_of_routing_shards`。
- 目标主分片数是源主分片数的整数倍，并满足 routing shards 的因数约束。
- Split 期间源索引需要停止写入并设置只读。
- 集群必须有足够磁盘容纳新旧两代短暂并存。

因此常见扩容路径是 `1 -> 2 -> 4 -> 8` 或 `4 -> 8`，不能使用 `N + 1` 任意加一个主分片。

### 10.3 可续跑状态机

```text
源代：WRITING -> SPLITTING -> RETIRED -> DELETED
目标：CREATING ----------------> WRITING
```

推荐流程：

1. 获取分区写锁，暂停该分区写入，不推进相关来源断点。
2. 同步 refresh 源索引，记录最新文档数和容量。
3. 创建更高代数的目标分区记录和物理索引。
4. 满足 Split 前提时调用 `_split`；否则调用异步 `_reindex`。
5. 将 ES 异步任务 ID 持久化到任务断点，进程重启后继续查询同一任务。
6. 校验文档数、Mapping、分片数、样本和查询结果。
7. 用一次 `_aliases` 请求原子切换全部相关读写别名。
8. 将目标代标记为 `WRITING`，恢复来源任务并成功写入至少一个批次。
9. 将源代标记为 `RETIRED`，经过观察期后删除旧物理索引。
10. 确认删除成功后，将源代标记为 `DELETED`。

遇到 `SPLITTING` 状态时，新的全量、增量、手工同步和失败重放应先幂等续跑扩容任务；续跑失败则本批退出，来源断点不得前移。

### 10.4 何时必须 Reindex

- 源索引没有预留足够的 routing shards。
- 目标主分片数不满足 Split 因数关系。
- 同时需要修改 Mapping、分析器或文档结构。
- 需要从有问题的旧设计迁移到新的分区命名或路由版本。

Reindex 前停止写入并 refresh，避免目标任务看不到最后一批已提交但尚未刷新可见的数据。任务完成后不能只看 API 成功状态，还要核对源目标文档数、失败项、版本冲突和抽样内容。

## 11. 故障重建

Split 是容量操作，故障重建是数据恢复操作。主分片永久损坏时，不应尝试根据 ES 内部分片编号猜测来源数据，而应重建该物理索引负责的完整业务时间范围。

通用流程：

1. 暂停相关写入任务并冻结断点，记录各来源重建上界。
2. 将旧代标记为 `REBUILDING`，查询明确进入失败或维护状态。
3. 使用相同业务时间边界和更高 `generation_no` 创建替代索引。
4. 从权威来源读取属于该时间范围、且不超过重建上界的全部记录。
5. 复用原路由版本、稳定 ID、字段转换和优先级规则写入新代。
6. 完成分区级校验后原子切换全部别名。
7. 恢复原同步任务，由旧断点追平重建期间产生的变更。
8. 观察确认后删除旧代。

为了让“按分区重建”真正可执行，权威来源应具备类似 `(business_time, source_id)` 的范围扫描索引，或提供可按业务时间高效扫描的数据副本。没有这项能力时，必须接受全表扫描和更长 RTO。

以下情况无法保证只重建一个分区：

- 业务时间被修改后没有旧分区删除记录。
- 稳定 ID 组成字段被原地修改。
- 来源更新游标无法发现旧行更新。
- 分区元数据的时间边界或路由版本不准确。
- 权威来源已经删除部分历史数据。

## 12. 蓝绿迁移实施流程

### 12.1 推荐开发顺序

1. 实现确定性规则核心、任务表和分区表。
2. 实现独立全量导入器、重建和校验能力。
3. 用代表性样本冻结稳定 ID、路由、Mapping 和分析器。
4. 改造查询目标解析、排序、分页和详情定位。
5. 实现长期增量同步及断点恢复。
6. 验证全量与增量重叠、失败重试和多来源并发。
7. 最后才启动正式全量回灌。

不要先导入全部历史，再发现 Mapping 或查询契约需要修改。任何稳定 ID、路由、Mapping 或来源优先级变化，都应重建受影响的试灌索引并重新验证。

### 12.2 新集群准备

- 核对 Elasticsearch 版本、插件、JVM、节点角色、磁盘、网络和 TLS。
- 初始化独立新集群，验证选主、分片分配和磁盘水位。
- 创建版本化 Index Template、最小权限账号、监控和告警。
- 校验 `cluster.routing.rebalance.enable` 等持久化集群设置，避免继承错误状态。
- 导入程序启动时校验预期集群名称或集群 UUID，防止误写旧集群。
- 预留全量导入、扩容和新旧代并存所需磁盘空间。

### 12.3 回灌与追平

1. 为每个来源创建独立全量任务并记录 T0。
2. 同时创建长期增量任务，从安全重叠区开始扫描。
3. 按来源和逻辑索引限速，持续观察 Bulk、Merge、Heap、磁盘和查询。
4. 按需创建物理分区，不允许 ES 使用默认 Mapping 自动建索引。
5. 全量到达 T0 后标记成功并停止，增量继续追平。
6. 完成分区级数据校验、查询对照和故障演练。

### 12.4 切换门禁

切换前必须同时满足：

- 所有全量任务成功，增量延迟达到目标。
- 没有未处理的 Bulk 失败或 `FAILED` 任务。
- 每个预期分区的主分片可用，别名与元数据一致。
- 分区级数量、按日分布、唯一键和样本校验通过。
- 核心查询在新集群完成真实关键词与过滤条件对照。
- 监控、告警、回滚配置和旧集群只读方案已验证。

### 12.5 切换与回滚

```text
暂停旧写入或进入最终追平窗口
-> 执行最后一轮增量
-> 冻结并核对来源游标
-> 灰度切换查询
-> 切换全部查询与写入
-> 旧集群只读观察
```

建议保留旧集群 `7-14` 天作为快速回退窗口，具体时长由数据变化速度和容量决定。

回滚触发条件至少包括：

- 新集群核心查询错误率或 P95/P99 超过门槛。
- 数据校验出现不可解释差异。
- 增量断点无法持续推进。
- 新集群磁盘、Heap、Merge 或分片状态不稳定。

回滚应整体切回旧查询与写入配置，不能让两个集群同时接收无协调写入。回滚后保留新集群现场和任务状态，先分析再决定续跑或重建。

### 12.6 旧节点复用

旧集群退出观察期后，如果需要把旧节点加入新集群：

1. 确认旧集群不再承担任何读写。
2. 停止旧节点。
3. 备份需要保留的配置和审计信息。
4. 清空旧集群数据目录。
5. 配置新集群名称、发现节点和证书。
6. 以空节点身份加入新集群并观察再平衡。

不能携带旧集群数据目录直接加入另一个集群。

## 13. 校验与验收

### 13.1 为什么不能只比总数

来源行可能因为业务唯一键去重、多来源合并、无效数据跳过或条件更新而与 ES 文档数不同。正确的校验单位是“最终文档规则”。

### 13.2 分区级校验项

- 按业务唯一键去重后的来源数量与 ES 文档数。
- 按日或更小时间粒度的数据分布。
- 最小/最大业务时间和来源观测游标。
- 多来源占比、优先级覆盖数量和跳过原因。
- 集合字段的去空、去重、排序和派生计数。
- 随机样本的正文、精确字段、展示字段和详情回源。
- Mapping 版本、路由版本、主分片数和最大主分片大小。
- 查询时间范围与实际目标别名集合。

### 13.3 必测边界

- 归档边界前一秒、边界时刻和后一秒。
- 固定短分区交界、月末、季度末和时区切换。
- 历史补录、晚到结果、重复扫描和任务重启。
- Bulk 部分失败、429、版本冲突和网络超时。
- 全量与增量同时写同一稳定 ID。
- 多来源高优先级先到与后到两种顺序。
- Split/Reindex 中断续跑和别名原子切换。
- 分区元数据存在但物理索引缺失。
- 主分片失败时查询不返回部分结果。
- 异常时间边界相等、越界和任务重启复用原边界。

## 14. 监控与告警

### 14.1 集群指标

- Cluster health、未分配分片、主分片 active 状态。
- Heap、GC、CPU、磁盘使用率和水位。
- Indexing pressure、Bulk rejection、线程池队列。
- Merge backlog、refresh、flush 和段数量。
- 每个物理索引总主存储和最大主分片大小。

### 14.2 同步指标

- 每个来源的当前断点、T0、每分钟来源行和文档写入量。
- 增量延迟、最近成功时间、连续失败次数。
- Bulk 请求字节数、耗时、item 失败率和重试次数。
- 无效记录、待补数据、来源冲突和解析失败数量。
- 当前运行、暂停、失败、Split、Reindex 和 Rebuild 任务。

### 14.3 查询指标

- 按逻辑索引和时间跨度统计 QPS、P95、P99、超时和错误率。
- 单次查询命中的索引数与主分片数。
- 全历史查询、深分页和高亮大字段查询占比。
- `partial shard failure` 必须产生错误与告警，不能只记日志。

## 15. 安全与配置

- 凭据不要写入本文、命令行历史、日志或可公开构建产物。
- 优先使用密钥管理、受控配置中心或运行环境注入；确需本地文件时限制权限并避免提交真实值。
- 全量导入使用专用最小权限数据库账号和 ES 账号。
- 导入器同时校验目标集群身份、允许的索引前缀和写入环境。
- 管理接口按任务编号和分区 ID 操作，不提供“删除全部并重建”类无边界入口。
- 日志记录任务号、逻辑索引、分区、游标和错误摘要，不记录密码、令牌或完整敏感正文。
- 切换、回滚、删除旧代和清理旧节点都应保留审计记录。

以下只用于第一次试灌，不是生产默认值：

| 参数 | 起始参考 | 调整依据 |
| --- | --- | --- |
| 目标单主分片 | `20-40 GiB` | 查询延迟、恢复时间、Heap、磁盘和 Merge |
| 自动扩容评估阈值 | 最大主分片约 `45 GiB` | 实际硬件和压测结果 |
| Bulk 请求体 | `5-15 MiB` | 文档大小、网络、拒绝率和写入延迟 |
| 来源批次 | `2,000-5,000` 行 | 关联查询、内存、转换耗时和 Bulk 字节数 |
| 单逻辑索引并发 | `1` 起步 | 429、Merge、磁盘和查询 P95 |
| 默认查询窗口 | `7` 天示例 | 产品需求和查询成本 |
| 旧集群观察期 | `7-14` 天示例 | 数据变化速度、磁盘和回滚要求 |

每次调整都应记录测试数据规模、Mapping 版本、节点规格和结果，避免脱离环境复制参数。

## 17. 常见故障处理

| 故障 | 正确处理 | 禁止行为 |
| --- | --- | --- |
| Bulk 部分失败 | 整批不推进断点，按同一规则重试 | 只看 HTTP 200 后推进断点 |
| 持续 429 | 降低并发和字节数，指数退避，检查 Merge/磁盘 | 无限制立即重试 |
| 创建索引成功但别名失败 | 保留任务状态，核对现状后幂等续跑 | 创建另一个随机索引继续写 |
| 元数据存在但索引缺失 | 明确失败、告警并进入重建流程 | 当成该范围无数据 |
| Split 中断 | 从持久化任务 ID 和状态续跑 | 清空任务表重新开始 |
| 不满足 Split 前提 | 创建下一代并 Reindex | 强行原地修改主分片数 |
| Mapping 变化 | 新建代数、重建、校验、切别名 | 在旧索引上假定不兼容字段会自动生效 |
| 业务时间跨分区修改 | 删除旧分区文档并写新分区，保证幂等 | 只写新分区留下重复数据 |
| 来源无更新游标 | 补可靠变更源或明确不支持更新 | 宣称 `id` 游标能发现旧行更新 |
| 新集群切换异常 | 整体回切并冻结现场 | 双集群无协调同时写入 |

## 18. 反模式清单

- 直接复制旧 ES 文档，却没有从权威来源验证新字段和去重规则。
- 删除在线索引后原地全量重建。
- 在业务代码中写死物理索引名或代数。
- 用同步时间、更新时间或当前时间决定业务分区。
- 依赖服务器默认时区。
- 使用深 `OFFSET` 扫描超大来源表。
- 让 ES 自动创建缺少正确模板的索引。
- 将索引总大小误当作最大主分片大小。
- 未预留 routing shards 却假定未来可以直接 Split。
- 只检查 Bulk HTTP 状态，不检查 item 结果。
- 先推进断点，再写 Elasticsearch。
- 用来源游标最小值和最大值声称可以完整重建时间分区。
- 将“无分区元数据”和“分区故障”都处理成空结果。
- 在没有副本和快照时低估节点故障会同时损坏多个主分片。
- 为未参与查询的字段建立全文索引或保存重复大字段。
- 在全量、增量、重试和重建中各自实现一套 ID 与路由逻辑。

## 21. 总结

Elasticsearch 大数据迁移的可复用能力，最终体现在四件事上：规则确定、状态可恢复、切换可回滚、数据可证明。

只要业务时间路由、稳定 ID、来源优先级和 Mapping 被统一版本化；全量、增量与重建共享同一套规则；所有物理代际变化都通过元数据和原子别名控制；验收使用分区级业务口径而不是表面总数，集群迁移就能从一次性工程变成可重复执行的标准能力。
